# 源码专利点挖掘

## 基本原则

以源码和用户提供的项目上下文为证据基础。不得把推测的设计写成已经实现的能力。每项内容必须标注为以下之一：

| 标签 | 含义 |
|---|---|
| 已实现事实 | 可由源码、测试、配置、运行记录或项目文档直接证明。 |
| 可落地增量 | 基于已证实代码缺口的有限扩展，必须列明需要新增的模块和接口。 |
| 探索方向 | 仅是问题或方向；在有证据前不得作为专利候选评分。 |

证据来源也必须标注：

| 来源 | 使用方式 |
|---|---|
| 源码地址/本地仓库 | 最高优先级；记录仓库、分支/提交、绝对文件路径和行号。 |
| agent CLI 对话 | 用于恢复设计背景、故障、取舍和未落地想法；必须与源码或原始记录区分。 |
| workspace/session | 用于发现跨会话需求、测试过程、错误信息、临时方案和反复出现的问题；记录 session 标识或可定位上下文。 |
| 项目文档、测试、MR、提交记录 | 用于证明需求、行为、边界和历史变更；不能替代运行代码对当前实现的证明。 |
| 专利、开源仓库、标准、论文 | 用于现有技术和常规性比对，不得反向伪造项目实现。 |

优先级顺序为：用户明确提供的源码地址 > 本地可访问源码 > agent CLI / workspace / session 原始记录 > 项目文档和提交记录。任何无法定位到原始材料的内容只能标记为“待核实”。

## 执行流程

### 1. 获取项目和会话数据源

先询问或识别用户提供的软件项目源码地址，可接受 Git 仓库 URL、本地目录、压缩包、MR/提交链接或多个项目地址。若没有源码地址：

1. 搜索当前 workspace 中可访问的项目目录和文件；
2. 从相关 agent CLI 对话恢复需求、故障、设计决策和已尝试方案；
3. 从可访问的 workspace/session 上下文提取反复出现的任务、错误、测试结果和未完成机制；
4. 必要时用 `git-ai-search` 恢复与代码提交相关的历史 AI 对话，但不得直接读取未经允许的原始会话日志目录；
5. 建立“来源索引”，为每条事实记录 `source_type`、项目/session 标识、时间、定位方式和可信度。

如果只能拿到对话而拿不到源码，先交付“对话证据候选池”，明确标注源码缺失；不能将其当作已实现技术点，也不能直接进入授权概率排序。

### 2. 建立范围和证据台账

1. 汇总项目源码、agent CLI 对话、workspace/session、文档、测试、MR 和提交记录中的原始证据。
2. 优先使用 `rg` / `rg --files`；阅读命中符号附近的代码，并追踪到存储、API 和运行时调用链。
3. 记录仓库、绝对 `文件:行号` 或对话/session 定位、观察到的行为、输入输出数据及限制。不得读取凭据或暴露密钥。
4. 对同一事实进行交叉验证：源码证明当前行为；对话/session 证明问题背景；测试或运行记录证明实际效果。
5. 若某一技术特征依赖未来改造，写明源码已证实的缺口及最小新增组件。

### 2. 建立 10–15 个候选池

先形成 10–15 个彼此独立的候选点，再收敛。每项必须包含：源码中可见的技术问题、现有机制及其边界；只有在属于有限增量时才提出候选机制。可行时至少给出两处源码佐证；否则标注为“探索方向”。

不得把同一泛化概念拆成表面变体。默认排除泛化的 LLM 使用、缓存、表单校验、参数映射、提示词模板、仪表盘和“AI 审查”；除非存在项目特有的技术机制使其足够具体。

### 3. 检索前初筛

按证据强度、技术具体性、实现可行性和预期现有技术拥挤度排序。保留前 6–8 个进入深检索；其余保留并说明原因。

### 4. 反复进行专利检索

#### 4.1 网页平台和登录态

默认使用用户指定的 [uyanip 专利检索平台](https://www.uyanip.com/)，除非用户另行指定平台。本次流程优先用 Computer Use 操作网页完成检索，不用未授权的接口替代网页证据。使用前必须阅读 `computer-use:computer-use`。

打开网站后先检查页面、登录态和检索入口：

- 已登录：继续进行检索和只读查看；
- 未登录、登录过期或平台要求验证码：在对话中明确提示用户“请在当前浏览器窗口完成平台登录/验证码操作，完成后回复我继续”，暂停检索；不得代填账号、密码、短信验证码或处理 CAPTCHA；
- 页面异常、权限不足或无法确认检索结果：记录阻塞原因，不得猜测命中数；
- 只做搜索、打开详情、查看摘要/权利要求等只读操作，不执行购买、下载付费内容、保存检索式、提交申请或其他外部写入。

每次 Computer Use 点击、输入检索式或打开详情后，重新读取页面状态，使用最新的页面元素定位，不能复用失效的元素索引。

在 uyanip 中优先记录页面上实际显示的检索表达式和结果条数；打开结果详情后，分别核对摘要、权利要求、法律状态和相似专利。若页面提供检索式保存、购买、下载或其他写入入口，只做只读查看，不点击提交。

#### 4.2 检索批次

对每个保留候选至少执行四组独立检索：

1. 精确技术机制短语；
2. 核心机制加实现名词；
3. 技术问题加解决机制；
4. 更宽泛的领域同义表达。

每组检索都要在网页上实际执行，并记录：检索式、命中数、检索日期、平台、国家/地区、筛选条件、页面截图或可定位页面信息、最接近的 1–3 件文献。交付时要展示检索效果，至少给出“检索式 → 命中数 → 近似案 → 是否进入下一轮”的结果链。

建议采用逐步收敛：先宽搜发现术语，再用技术动作、数据结构、触发条件和技术效果收窄；不能只搜索候选标题。对零命中、1–5 件、较高命中三种情况分别记录：

- 零命中：可能是术语不一致，必须用同义词或拆分技术链复核；不能直接认定新颖；
- 1–5 件：打开全部或主要近似案，优先阅读摘要和独立权利要求 1；
- 命中较多：增加限定条件，直到能区分核心技术链或确认现有技术拥挤。

低命中仅是进入下一轮的条件，不等于具备新颖性。必须打开近似文献，阅读独立权利要求 1 后再给出新颖性或授权判断。

如果近似文献的独权覆盖候选的完整技术链，淘汰或降级；若只重合通用部件，明确写出未重合的技术链。

### 5. 谨慎使用开源和公开资料

专利检索稀少或含糊时，可搜索相关开源仓库、标准、论文和公开技术文档，用于判断机制是否常规、补足实现术语、寻找真实故障模式。它们不能替代专利检索。

若没有候选通过筛选，交付 3–5 个探索方向：项目已证实的问题、拟追求的技术效果、缺少的实现证据以及下一步源码调查点；不得虚构权利要求语言。

### 6. 独立评审子 agent

仅在证据台账和检索记录完成后启动一个隔离的子 agent。向其提供原始源码片段/路径、检索记录和候选表，但不提供首选排序。

要求其识别：无源码支撑的实现表述、与近似独权的重叠、技术效果是否由机制必然导出、以及淘汰每个头部候选的最强理由。将意见保留为“评审结论”，不得静默覆盖。

## 交付要求

交付排序前五（不足五个则如实交付）和完整候选池附录。每个头部候选必须包括：

| 字段 | 内容 |
|---|---|
| 拟定主题 | 窄化的技术标题，不使用营销名称。 |
| 项目/数据源依据 | 源码仓库和绝对 `文件:行号`，或 agent CLI/workspace/session 的可定位原始记录。 |
| 当前行为与缺口 | 仅陈述事实，包括故障或限制。 |
| 候选机制 | 标注为“已实现事实”或“可落地增量”。 |
| 技术效果 | 具有因果链，可度量或可观察。 |
| 检索记录 | 检索式、命中数、近似案、独权对比。 |
| 检索效果 | 网页实际操作结果：平台登录状态、检索批次、命中数变化、筛选条件、详情页核验结果；如因未登录暂停，记录用户待操作提示。 |
| 受理前景 | 高/中/低及依据。 |
| 授权前景 | 高/中/低及创造性风险；不得承诺授权。 |
| 创新点 | 未被近似案覆盖的技术链。 |
| 评审结论 | 独立评审挑战及处理结果。 |
| 下一步 | 写交底、继续查源码、补充检索或淘汰。 |

概率仅作内部初评，不得表述为法律意见或授权保证。所有本地源码证据都应使用绝对路径和行号链接。

## 停止条件

- 不得只因某条检索式为零命中就推进候选。
- 未经代码证明，不得声称项目已实现版本化、迁移、兼容、语义匹配或自动修复。
- 近似独权覆盖完整技术链且不存在源码支撑的差异点时，不得建议申报。
- 不得虚构命中数、专利号、权利要求内容、代码位置、基准数据或子 agent 结论。
